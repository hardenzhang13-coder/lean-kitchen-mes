# 精益厨房 V3 — 单位体系与供货关系设计

> 本文档是采购与库存彻底重构的地基。重构前必须先冻结本文档中的决策。
> 版本：v1.0 | 2026-11-07 | 状态：待用户确认

---

## 一、背景与问题

采购与库存重构前，必须先解决食材（原料/调料）的单位管理，现状存在三个结构性问题：

1. **单位职责混在一张表上**：`ingredients` 同时承载"怎么记账"（stock_unit）和"怎么买"（purchase_unit / purchase_spec / units_per_purchase），而"怎么买"本质是供应商给定的包装，不是食材的属性。
2. **换算系数依赖文本解析**：`spec-parser.ts` 从「200g/袋*10袋」自由文本中正则解析系数，文本写法变化会导致换算静默失效。
3. **排程拆解与库存记账的桥梁不明确**：排程产出克，库存按库存单位记账，中间缺少强制、显式、可追溯的换算规则。

> 现有采购/库存功能仅用于演示，无实际业务数据约束，重构时可直接替换模型，不做兼容迁移（除本方案第五节所述字段搬家）。

---

## 二、核心原则

### 原则 1：一个食材同时活在三套单位体系，必须显式分离

| 体系 | 单位 | 用途 | 归属 |
|------|------|------|------|
| 计算单位（克） | g | 排程拆解、菜品 BOM、成本核算 | 系统内部语言 |
| 库存单位 | 瓶 / 袋 / 斤 | 库存表、台账、出入库记账 | 食材档案 |
| 采购单位 | 件 / 箱 / 板 | 下单、验收、应付 | 供应商供货关系 |

### 原则 2：库存单位是唯一记账基准

- 一种食材**只有一个库存单位**，全局唯一。
- 入库、出库、台账强制换算到库存单位；页面上不允许出现"用采购单位记库存"的入口。
- 库存单位一旦有台账流水即不可修改（需数据修复流程，不在常规编辑范围）。

### 原则 3：换算系数显式存储，禁止运行时解析文本

- 采购单位 → 库存单位：`1 采购单位 = N 库存单位`，N 为数字字段，录入必填。
- 库存单位 → 克：`每单位净含量（克）`，重量类必填。
- 采购规格文案（如 1.9L*6）仅作展示，不参与任何计算。

### 原则 4：单据快照当时的换算关系

采购入库单明细冗余保存：采购单位、采购单价、换算系数 N、库存单位。
档案或供货关系后续变更不影响历史单据的理解与重算，台账永远对得上。

### 原则 5：散称是退化形态，不是特例

散称食材：采购单位 = 库存单位，N = 1，净含量换算走克。
默认按散称处理，只有存在供应商供货关系时才出现采购包装。

## 三、模型设计（方案 B：供货关系层）

### 3.1 `ingredients` 字段调整

**保留**（记账与计算相关）：
- `stock_unit` → 语义明确为**库存单位**（唯一记账基准）
- 新增 `grams_per_unit` decimal(10,2)：每库存单位净含量（克），出库扣减与成本换算用
- `latest_ref_price`：参考零售价（元/库存单位），仅作排程估价参考

**移除**（搬迁至供货关系）：
- `purchase_unit`、`purchase_spec`、`units_per_purchase`、`default_supplier_id`

> 调料（seasoning）/ 酱料（sauce）外购部分同样适用：各自的 `purchase_unit`/`purchase_spec` 字段同口径搬迁。

### 3.2 新增 `supplier_ingredients`（供应商供货关系）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int PK | |
| ingredient_id | int | 关联食材 |
| supplier_id | int | 关联供应商 |
| purchase_unit | varchar(20) | 采购单位（件/箱/板） |
| purchase_spec | varchar(100) | 采购规格文案（1.9L*6），仅展示 |
| units_per_purchase | int | **1 采购单位 = N 库存单位**，必填 ≥ 1 |
| purchase_price | decimal(10,2) | 采购单价（元/采购单位），最近成交价参考 |
| is_default | bool | 是否该食材默认供应商（同食材唯一） |
| created_at / updated_at / deleted_at | timestamp | 软删除 |

约束：
- `(ingredient_id, supplier_id, deleted_at)` 唯一；同食材同供应商允许多条有效供货记录（不同包装，采购时选用）
- 同食材最多一条 `is_default = true`

### 3.3 采购入库单明细快照

`purchase_receipt_items` 增加/确认：
- `purchase_unit`、`purchase_price`、`units_per_purchase`、`stock_unit`（快照）
- 入库数量（库存单位）= 采购数量 × 快照 units_per_purchase

### 3.4 单位字典（units 表）

- 分类保留：weight（必须有 grams_per_unit）/ volume / count
- 体积单位不直接参与克换算；液体调料的克换算一律走食材档案的 `grams_per_unit`（录入时按净含量克数，如 1.9L 生抽按约 2200g 折算或按标签净含量录入）

## 四、业务流

### 排程拆解（不变）
理论用量（g）→ ÷ grams_per_unit → 需求库存单位数。不碰供应商。

### 采购计划（方案 B 的价值点）
- 有默认供货关系 → 带出默认供应商，按系数换算采购量并估价：需求 17 瓶、每件 6 瓶 → 建议采购 3 件
- 同食材多条供货关系 → 采购员可选，计划阶段即可比价（同需求不同买法，金额不同）
- 无供货关系 → 按散称处理，采购数量 = 库存单位数

### 采购单与入库
- 采购单明细 = 食材 + 供应商 + 快照（采购单位/单价/系数）
- 入库：库存单位数量 = 采购数量 × 快照系数；库存增加 + 台账写入在同一事务
- 采购单上可直接新建/更新供货关系（降低录入门槛，录入时机跟随真实采购行为）

### 出库（不变）
切配工单按克扣减 → ÷ grams_per_unit → 库存单位扣减。

## 五、现状迁移（重构实施时执行）

1. 有 `default_supplier_id` 的食材：生成一条 `supplier_ingredients` 记录，`purchase_unit`/`purchase_spec`/`units_per_purchase` 原值搬入，`is_default = true`
2. 无默认供应商的食材：不迁移，自然退化为散称
3. 食材表删除已搬迁字段，新增 `grams_per_unit`（存量数据需按食材类别批量初始化 + 人工核对）
4. `spec-parser.ts` 不再参与采购入库换算，逐步下线（保留期间仅作录入辅助提示）

## 六、待确认事项

1. **grams_per_unit 初始化**：存量食材的"每库存单位净含量"无可靠来源，需按类别给默认值（如 瓶=500、袋=200？）还是强制人工逐条录入？建议：先按类别默认值批量填，列表页高亮标记"待核对"。
2. **调料/酱料表**：是否同步并入本体系（调料库存也按瓶/袋记账 + grams_per_unit），还是调料本次只做字段口径对齐、模型后续再合？建议：一次合入，避免二次重构。
3. **采购计划合并规则**：同一食材多条供货关系时，计划默认走 is_default 还是允许多供应商拆单？建议：MVP 阶段一律走默认供应商，比价仅作展示。
