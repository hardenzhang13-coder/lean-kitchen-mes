## 一、讨论背景

本周试运行暴露三个问题：

1. **生产不是"生产"**：切配中心基于门店菜品排程单 + 切配中心实际库存量决定生产计划，而不是几个单据的简单汇总；班组长需要能基于库存量灵活调整生产计划单数据。
2. **"内部生产单"这个实体难以理解**，名称混淆、晦涩。
3. **净菜出库机械**：切配中心自己内部生产的，出库只能选切配中心主体，与实际业务不符。

三者同源：**实体是按"单据长什么样"切分的，不是按"业务角色"切分的**。

## 二、现状诊断（代码核实结论）

### 2.1 三处结构性错位

#### 错位 A：生产计划单是「汇总快照」，不是「生产计划」

- `lib/server/production-plan-utils.ts` → `buildProductionPlanData()` 对切配行只做 `cAgg.requiredQty +=`，**全程不查询 `prepped_stock`（净菜库存）**。
- 后果 1（库存不参与）：切配中心成品仓里的净菜，对当天生产量**零影响**。门店排程需 150 份青椒丝，仓里已有 100 份，系统仍计划切 150 份 → 系统在诱导过量生产。
- 后果 2（不可编辑）：`production_plans.cuttingJson` 是 JSON blob，生成即固化。班组长唯一能改数量的入口是「完成生产」弹窗——**事后**回填，缺失**事前排产**这一层。
- 后果 3（跨日期汇总无归属）：允许把不同日期的排程汇总到同一生产日期，而需求日期在快照中丢失 → 后续配送无法回溯"这批货是哪天的需求"。

#### 错位 B：实体按单据类型切，而非按业务角色切

```
门店排程单 ──┐
             ├──▶ 生产计划单（跨店汇总快照）──▶ 完成生产 ──▶ 净菜入库 ──▶ 出库单
内部生产单 ──┘
```

- 「内部生产单」内容实质只有：**一批没有门店归属的净菜生产量**。
- 却被做成有独立状态机（待生效/进行中/已完成）、独立编号（`SPO-*`）、独立「纳入生产计划」流程的完整单据。
- 产生三段割裂链路：建单 → 纳入 → 完成，且必须先「纳入」才生效。
- 命名上「内部」= 内部于切配中心？内部于生产计划？内部于门店？使用者必须猜。

#### 错位 C：出库单的主体维度设计反了

- 业务事实：**净菜从切配中心发给门店**。
- 当前 `outbound_orders.subject_type = 'store' | 'cutting_center'`。
- 「切配中心主体」是**为内部生产单找的接盘者**：内部生产的东西不挂任何门店，出库时"收货方是谁"无解，只好造一个"切配中心"当收货方。
- 现实中不存在「把净菜出库给切配中心」→ 用户感到"跟实际业务非常不符"，准确。

### 2.2 数量口径散落三处

| 位置 | 字段 | 语义 |
|---|---|---|
| `cutting_orders` | `required_qty` | 门店级净菜需求量 |
| `production_plans.cuttingJson[]` | `requiredQty` | 跨店合并后的需求快照 |
| `outbound_order_items` | `required_portions` | 出库时的"计划量" |

生产完成时 `actualQty` 按各店需求量**占比**回写到 `cutting_orders`（展示级精度），出库时"未切配/量不足"又依赖这个回写的 `status`。链路越长，口径越糊。

### 2.3 现有页面的字段冗余实证（字段审查的起点）

代码核实到的**具体**字段冗余，不是推测：

| 位置 | 现状字段 | 问题 |
|---|---|---|
| 出库单详情表 | 「计划出库数（份）」+「计划量」+「本次出库数（份）」+「出库量」 | **四列并存**。决策只需要一个「本次出库（份）」。克重列是历史遗留（记账主单位早已定为份），且"计划量(g)"与"计划出库数(份)"业务人员分不清哪个是依据 |
| 出库单详情表 | 「一级分类」「二级分类」「序号」 | 分类是档案属性，出库作业不据此决策；「序号」是排版用序号，出现在明细行毫无意义 |
| 出库单列表 | 「序号」「出库主体」「来源单据」「是否按计划出库」 | 「序号」纯排版噪音；「出库主体」在新模型下恒为门店（信息量为零）；「是否按计划出库」= 逐行比对结果，应由「本次出库 vs 应出量」自然表达 |
| 切配工单表 | 「一级分类」「二级分类」「编号」「规格」+「计划份数」「净料用量」 | 分类/编号与名称重复表达；份与克两套单位并存 |
| 生产计划卡片 | 「X 张排程」「Y 张内部生产」 | 「内部生产」概念即将消失；且"张排程"对班组长无决策价值 |
| 库存列表 | 「一级分类」「二级分类」「编号」「名称」「类型」+「库存份数」「库存量」 | 5 列档案属性 + 2 列数值；库存管理场景真正要的是"这个净菜有多少、能给谁" |
| 台账 | 「变动份数」「变动量」「结存份数」「结存量」 | 份 + 克 四列；出库流水场景以份为主，克为辅 |

**共性问题：把"档案属性"和"决策字段"平铺在同一张表里。** 业务人员在每一张表都要先做一次"哪些列跟我有关"的筛选——这就是"棘手"的来源。

## 三、重构后的目标模型

### 3.1 核心概念分离一：批次 ≠ 库存

> **生产批次 = 执行单元**（谁、何时、切哪几行）
> **净菜库存 = 共享池**（不分批次，一份数据）

- 多个批次互不影响，也**互不隔离库存**。
- 完成生产 → 入库进**共享池**，台账记来源批次号（可溯源，但不分割库存余额）。
- 出库 → 从**共享池**扣减，台账记来源出库单号。
- 因为共享池 + 多批次，**每张批次单算"可用库存"时必须扣掉已被其他批次占用的部分** → 必须做全局占用。

### 3.2 核心概念分离二：批次是主体，日期是属性（结论 C2）

方向不能搞反：

| | 错误理解 | 正确理解 |
|---|---|---|
| 组织维度 | 一天 = 一个生产计划 | **一个生产计划单 = 一个生产批次**；一天可有 N 个批次 |
| 日期的角色 | 主键（按天生成/汇总） | **批次的一个属性**（生产日） |
| 批次之间的关系 | 同一天的计划是同一张 | 彼此独立：不同行、不同状态、不同进度 |
| 列表呈现 | 按天分组 | **按批次平铺**，日期只是筛选维度 |
| 编号语义 | `PPL-20261120-001`（11-20 的计划） | `BC-000123`（**第 123 号生产批次**） |

推论：
- **批次 ↔ 排程单 = N:M**：一张排程单的需求可被拆进多个批次；一个批次也可纳入多张排程单。
- 批次与需求日不做强约束（B2）：常态为生产日 +1。
- 侧边栏「生产」更名「**生产批次**」；取消「内部生产单」后，生产模块不再需要双页签结构。

### 3.3 核心概念分离三：排程单 ↔ 出库单 = 1:1（结论 D1）

**一张排程单只能对应一个出库单**，这是业务现状，不是系统限制。

推论：
- 出库单 ↔ 排程单 = **1:1**（不再是上一版的 N:1）。
- 「分批多次出库」**作废**。一张排程单的净菜需求，一次性由一张出库单结算。
- 因此出库明细里的「已出」字段**必然为 0**（该排程单还没出过库）——这从数据上证实了 §7 的判断：**该字段是纯噪音，应删**。
- 若某次出库因库存不足只出了一部分 → **这是业务缺口，不是"还能再出一次"**。缺口的处理是：记入履约进度（需求 → 已备货 → 已出库，缺口标红），由门店侧决策（减份/换菜/次日补）。
- 一张排程单出库完成后，该排程单状态 → 已完成。

### 3.4 目标实体关系

```
┌─ 需求层 ─────────────────────────────────────────────┐
│  门店排程单（唯一需求入口，需求日 = scheduleDate）      │
│    └─ 门店级净菜需求行（cutting_orders，需求量 demand） │
│       字段：需求量 / 已备货量 / 已出库量 / 履约状态      │
└──────────────────────┬─────────────────────────────┘
                       │  纳入（可拆分：N:M）
                       ▼
┌─ 生产层 ─────────────────────────────────────────────┐
│  生产批次单（= 生产计划单，一天多个，彼此独立）          │
│    planDate = 生产日（常态 = 需求日 D-1，不强校验）      │
│    ├─ 需求行  ← 来自门店排程汇总，可下钻到店/菜          │
│    └─ 自主备货行 ← 切配中心自定，无门店归属（替代内部生产单）│
└──────────────────────┬─────────────────────────────┘
                       │  完成生产（回填实际产量）→ 入共享池
                       ▼
┌─ 库存层 ─────────────────────────────────────────────┐
│  净菜库存共享池（prepped_stock，按 net/minor 聚合，唯一）  │
│    现有份数 current / **已被批次占用 reserved** / 可用     │
└──────────────────────┬─────────────────────────────┘
                       │  按【门店需求】配送（1 排程 ↔ 1 出库）
                       ▼
┌─ 出库层 ─────────────────────────────────────────────┐
│  出库单 = 切配中心 → 门店（主体恒为门店）                │
│    排程出库：scheduleId 必填，一对一                       │
│    手工出库：scheduleId 为空，全手工行                    │
└──────────────────────────────────────────────────────┘
```

### 3.5 数量口径的单一真源

| 数量 | 归属 | 定义 | 谁来改 |
|---|---|---|---|
| 需求量 `demand` | 门店排程单的需求行 | 菜品份数 × BOM 净料用量 → 份 | 门店/厨师长 |
| 可用库存 `available` | 库存共享池 | 现有 − 已被其他批次占用 | 系统 |
| 建议生产 `suggested` | 批次行（派生） | `max(0, 需求 − 本行可分配到的可用库存)` | 系统算 |
| 计划生产 `plan` | 批次行 | 班组长编辑，默认 = 建议 | **班组长** |
| 实际生产 `actual` | 批次行 | 完成生产回填 | 切配执行 |
| 已备货 `prepared` | 门店需求行 | 该需求已被批次产出的份数 | 生产完成时回写 |
| 已出库 `shipped` | 门店需求行 | 该需求已配送份数 | 出库时回写 |
| 出库量 | 出库单明细 | ≤ 应出量，且 ≤ 可用库存 | 库管 |

### 3.6 「内部生产单」：取消实体，降级为行类型

**取消「内部生产单」独立实体**，其唯一能力降级为批次单里的**「自主备货行」**（`rowKind = stock`）。

| 属性 | 取值 |
|---|---|
| 需求日 | 空 |
| 需求量 | 0 |
| 关联的门店需求行 | 无 |
| 计划生产量 | 班组长手填 |
| 可用库存 | 仍显示（供参考） |
| 建议生产量 | 无意义（无需求可抵扣），显示 "—" |
| 完成后 | 入库为**自由库存**（不占用 reserved），可被任意门店出库以手工行带走 |

理由：业务内容 = 生产计划里一行「无需求来源的生产量」，独立建单是过度建模；独立实体带来三段割裂链路与独立状态机，却并无独立生命周期；取消后批次单成为唯一生产作业单，"内部"这个需要解释的名词自然消失。

## 四、库存占用机制

### 4.1 为什么必须硬占用

多批次 + 一份共享库存 ⇒ 若各批次独立计算可用量，同一份 50 份会被两张批次单各承诺一次 → 实际不够。

### 4.2 字段与算法

`prepped_stock` 增加：

| 字段 | 含义 |
|---|---|
| `current_portions` | 现有份数（实际在仓） |
| `reserved_portions` | **已被批次单承诺、尚未配送的份数** |
| 可用份数 | `current − reserved` |

批次单**确认时**的分配算法（逐行）：

```
全池可用 = Σ(current − reserved)
本行可分配 = max(0, 全池可用 − 本单已分配)
本行占用   = min(需求量, 本行可分配)      ← 写入 reserved
建议生产   = 需求量 − 本行占用             ← 需要新切的量
```

- **重算时机**：必须在「确认」时重算，不能在创建时算。提供「按实际库存重算建议量」。
- **释放时机**：批次单作废/删除 → 释放全部占用；完成生产时按实际产量核销。
- **跨天不清零**。
- **自主备货行不参与占用**，完成后为自由库存。

### 4.3 完成生产时的核销

```
实际产量 actual 入库 → current += actual
本行占用中「由现有库存满足」的部分 → 释放（货已在仓，直接用于配送）
actual 超出占用部分 → 成为自由库存（不占用）
actual 不足占用部分 → 缺口，释放差额并回写门店需求行的「已备货量」
```

### 4.4 分配示例

需求 150 份青椒丝，库存 100 份，拆两个批次：

| 批次 | 本行需求 | 可分配 | 占用 | 建议生产 |
|---|---|---|---|---|
| BC-001 | 50 | 100 | 50 | 0 |
| BC-002 | 100 | 50（100−50 已占） | 50 | 50 |
| 合计 | 150 | — | 100 | 50 |

总供给 = 库存 100 + 新切 50 = 150 = 需求。正确。

## 五、生产批次单详细设计

### 5.1 定位

| | 现在 | 目标 |
|---|---|---|
| 本质 | 多张排程单的跨店汇总快照 | 切配中心的**生产批次任务单** |
| 组织维度 | 一次汇总一张，可跨日期 | **一个批次一张**；批次是主体，日期是属性 |
| 是否读库存 | 否 | **是**，且扣除其他批次已占用 |
| 行是否可编辑 | 否（JSON 固化） | **是**，班组长改计划生产量 |
| 行来源 | 合并后无法区分 | 每行标注 `demand` / `stock` |
| 来源关系 | 排程 → 计划 一对一 | **排程 ↔ 批次 N:M** |

### 5.2 批次属性（结论 D2：去掉班组）

| 字段 | 说明 |
|---|---|
| 批次号 | `BC-000123`（全局流水，强调"第几号批次"） |
| 生产日 `planDate` | 批次属性之一，常态 = 需求日 D-1 |
| 计划时段 | 早班/中班/晚班/自定义；**可为空**（不强制） |
| 状态 | 草稿 / 已确认 / 已完成 |

> **不设班组字段**——当前没有班组实体，班组归属是人事概念，不属于生产作业单的核心信息。将来若引入班组，再作为生产资源维度扩展，不在本次范围。

### 5.3 批次行表（替代 `cuttingJson` 快照）

| 字段 | 含义 |
|---|---|
| `planId` / `sourceType` / `sourceId` | 批次 + 净料标识 |
| 名称/编码/规格/分类 | 净菜档案快照 |
| `demandDate` | **需求日期**（需求行来自排程单 scheduleDate；自主备货行为空） |
| `demandPortions` | 需求量（跨店汇总） |
| `availableStock` | 确认时可分配到的库存份数 |
| `suggestedPortions` | 建议生产量（自主备货行为空） |
| `planPortions` | **计划生产量（班组长可编辑）**，默认 = suggested |
| `planRemark` | 差异说明 |
| `actualPortions` | 实际生产量 |
| `rowKind` | `demand` / `stock` |
| `status` | 待确认 / 已完成 / 未完成 |

**批次行 ↔ 门店需求行 关联表**

| 字段 | 含义 |
|---|---|
| `planItemId` / `cuttingOrderId` | 批次行 / 门店需求行 |
| `portions` | 该批次行中，此需求行占多少份 |

作用：① 需求下钻 ② 精确回写「已备货量」③ 出库时定位待出需求 ④ 支持同一排程单需求拆入多个批次。

### 5.4 创建流程：清晰直观的交互与数据交互（结论 D3）

D3 的要求不是"加一个预览面板"，而是**创建这个功能本身在交互上和数据上都要说得通**。因此先定义它到底在做什么：

#### 5.4.1 这个功能的本质

> 创建生产批次 = **回答两个问题**：
> ① 这次生产**为谁而做**（承接哪些排程单的需求）
> ② 这次**额外做多少**（无排程单来源的自产/备货）
> 并且**当场让用户看到**这两个问题的答案（要切什么、切多少、库存够不够）。

一切交互设计都服务于让这两个问题**一眼可答**。

#### 5.4.2 数据交互：新建动作到底写了什么

必须让"创建"这个动作的数据后果可预期、可解释：

| 动作 | 写入 | 不写入 |
|---|---|---|
| 勾选排程单 | 暂存于前端选择态 | **不写库**（未创建批次前无任何持久化） |
| 填写批次属性 | 暂存于前端 | 不写库 |
| 点【创建批次】 | `production_plans`（草稿）+ `production_plan_items`（行）+ 批次行↔需求行关联 + 批次↔排程单溯源 | **不写库存、不写占用、不改排程单状态** |
| 后续【确认批次】 | `prepped_stock.reserved_portions` 占用 | 不改已备货量 |
| 后续【完成生产】 | 净菜入库 + 回写已备货量 + 核销占用 | — |

**关键承诺（必须在界面上让用户知道）**：
- 创建 ≠ 占用库存（占用发生在确认）
- 创建 ≠ 锁定排程单（锁定发生在确认）
- 创建后仍可自由增删行、增删来源（草稿态）

#### 5.4.3 交互结构：单页三区，所见即所得

不用弹窗（排程单分页 + 汇总表塞不进弹窗），不用多步向导（来回切换会丢失上下文）。**单页三区**：

```
┌─ ① 批次属性 ──────────────────────────────────────┐
│ 生产日 [今天▾]   计划时段 [早班▾]  (可空)           │
└────────────────────────────────────────────────────┘
┌─ ② 为谁而做：来源排程单 ──────┐┌─ ③ 做多少：汇总 ─┐
│ 需求日 [生产日+1▾] 门店[全部▾]││ 5 种净料 · 450 份 │
│ 🔍 搜索                        ││ 库存覆盖 200 份   │
│ ☑ 新金食堂 11-21 · 8菜 120份 ││ 建议生产 250 份   │
│ ☑ 明天吃啥首店 11-21 · 6菜90份││──────────────────│
│ ☐ 新金食堂 11-22 · 5菜 60份  ││ 净料  需求 库存 建议│
│                              ││ 青椒丝 150  100  50 │
│ ───────────────────────────  ││ 肉丝   80    0  80 │
│ ＋ 自主加一行（无排程单自产） ││ ⚠ 肉丝缺口 80 份  │
└──────────────────────────────┘└──────────────────┘
[取消]                                          [创建批次]
```

交互细则：
- **② 区**：排程单候选列表，多选；每条显示门店、需求日、菜品数、总份数、状态。勾选**立即**反映到 ③ 区。
- **③ 区**：随勾选实时重算（所见即所得，不需要点"预览"按钮）。列：净料 / 需求量 / 可用库存 / 建议生产 / 缺口标记。顶部 4 个汇总数（种类、需求份数、库存覆盖、建议生产）。
- **自主加一行**：在 ② 区下方，**独立于排程单选择**。加完立即出现在 ③ 区。这是"无排程单也能生产"的入口（C1），必须在同一屏内可见可点。
- **就地提示**（不弹窗、不阻断）：
  - 需求日早于生产日 → 黄条提示"含 2 张排程的需求日早于生产日，请确认"（B2 不强拦）
  - 库存不足 → 行内红标 + 顶部汇总"⚠ 1 种净菜存在缺口"
  - 该时段库存已被其他批次占用 → 提示已占用份数
- **入口**：从排程详情点「纳入生产批次」→ 跳此页并预选该排程。

#### 5.4.4 三个建批次场景走同一条路径（C1）

| 场景 | 操作 | 结果 |
|---|---|---|
| A 标准排产 | 选 N 张排程单 | 只有需求行 |
| B 排产 + 额外备货 | 选排程单 **+ 自主加一行** | 需求行 + 自主备货行 |
| C 纯自产（无排程单） | **不选排程**，直接自主加行 | 只有自主备货行 |

### 5.5 批次详情页 = 班组长工作台

**Tab 1「生产任务」**

| 净料 | 规格 | 需求量 | 可用库存 | 建议生产 | **计划生产** | 差异 | 状态 |
|---|---|---|---|---|---|---|---|
| 青椒丝 | 200g/份 | 150 | 100 | 50 | **[ 50 ]** | — | 待确认 |
| 肉丝 | 300g/份 | 80 | 0 | 80 | **[ 60 ]** | 少20： | 待确认 |

- 「计划生产」**可直接编辑**，改完实时联动：差异列显示与建议量之差；少切 → 「A 店将短交 20 份」；多切 → 「超出需求 30 份，转为库存」；「采购需求」原料量同步下降。
- 库存不足行标黄；`plan < suggested` 标红。
- 行可展开 → 需求下钻：哪家店、哪道菜、多少份。
- 行操作：`自主加一行`、`删除`。
- 顶部工具：`按建议量一键填充`、`按实际库存重算建议量`。

**Tab 2「门店需求」** — 跨店矩阵（净料 × 门店）。

**Tab 3「采购需求」** — 由**计划生产量** × 出成率折算原料采购量。

**Tab 4「生产回执」** — 完成生产录入实际产量。

### 5.6 重构的附带收益：采购量真正随生产计划走

现状采购量 = 毛需求，**完全不减库存**（`stockDeducted` 恒 0）。
重构后采购量 = Σ(计划生产量 × 出成率)。库存充足 → 少切 → **少买**。

## 六、出库单详细设计

### 6.1 约束

| 规则 | 说明 |
|---|---|
| 主体 | **恒为门店**（排程出库由排程单决定；手工出库由库管选择） |
| 与排程单关系 | **1:1** —— 一张排程单只能对应一个出库单（D1）。**不合并、不多次** |
| 无排程单 | **手工出库**（`scheduleId = null`，全手工行），始终允许 |
| 自主备货货 | 同样可补给任意门店（手工行，标记「备货补给」） |
| 「切配中心主体」 | **删除** |
| 库存不足 | 允许少出，**差额即业务缺口**（不是"还能再出一次"），记入履约进度 |

### 6.2 两种出库形态

| | 排程出库 | 手工出库 |
|---|---|---|
| 关联排程单 | 是（唯一一张） | 否 |
| 明细来源 | 该排程单的未出库需求行 | 全部手工录入 |
| 典型场景 | 按门店排程正常配送 | 门店加急补货、备货补给、无排程单的临时配送 |
| 库存扣减 | 先核销该需求行的占用，再动自由库存 | 直接动自由库存 |

### 6.3 交互（2 步）

**Step 1 选收货门店**
- 门店卡片列表；每张卡片显示该店**待发净菜份数**与**可出量**。
- 原「切配中心主体」卡片删除。

**Step 2 确认出库明细**（按 §7 纪律精简后）

排程出库：

| 净料 | 规格 | 应出量 | 本次出库 | 单价 | 金额 |
|---|---|---|---|---|---|
| 青椒丝 | 200g/份 | 150 | **[ 100 ]** | 1.20 | 120.00 |

- **删「已出」列**：由 D1，该字段在创建时**必然为 0** → 纯噪音。
- **删「可出量」列**：作为输入框 `max` 限制 + tooltip。
- **删克重列**（「计划量(g)」/「出库量(g)」）：记账主单位是份，克仅在台账保留。
- **「缺口」→ 底部汇总条**：应出合计 / 本次出库合计 / 缺口合计 / 合计金额。
- 「+ 手工加行」→ 选净料 + 填份数。

手工出库：

| 净料 | 规格 | 可用库存 | 本次出库 | 单价 | 金额 |
|---|---|---|---|---|---|

（无「应出量」——没有需求约束；「可用库存」在此是决策依据，必须单列）

### 6.4 库存扣减与占用核销

| 行来源 | 扣减规则 |
|---|---|
| 排程需求行 | 先核销该需求行对应的**占用**，不足部分再动自由库存 |
| 手工行（备货/加急） | 直接扣自由库存（`current − reserved`），不动任何占用 |

作废出库单：回退已出量、恢复库存、回写需求行「已出库量」（红线：作废 ≠ 删除）。

### 6.5 切配中心自用 / 损耗（待确认）

结论 B4 提到"切配中心也可自己出入库"。若存在**内部领用 / 报损 / 试菜**场景，这属于「无门店主体的库存出账」，与旧版被否的「切配中心主体出库」语义不同（旧版是给自产货找假收货方，此处是真实的内部消耗）。
→ 建议独立为**领用出库**（`type = 领用`），主体=切配中心，无排程来源。

### 6.6 状态

`已出库` → `已作废`（作废回滚库存）。`storeId` 恒非空；`selfOrderId` 取消。

## 七、字段设计纪律 —— 全系统审查规范（结论 D4）

### 7.1 升格：从"单表纪律"到"系统级规范"

字段纪律**不是**出库表一处的整改，而是**面向系统每一张表、每一个表单**的审查规范。本节定义规范本身，§7.2 是本次重构范围内各页面的逐页审查结论。

### 7.2 三档分类

每个字段必须先归入一档：

| 档 | 定义 | 呈现规则 | 例子 |
|---|---|---|---|
| **决策字段** | 用户在这一屏要做的选择 | 最显眼、可编辑、给默认值 | 本次出库量、计划生产量 |
| **约束字段** | 决策的边界条件 | 必须有，但不喧宾夺主（做 max 限制 / 提示 / 汇总） | 可出量、可用库存、应出量 |
| **历史/上下文字段** | 过去发生的事、静态档案 | **能挪走就挪走**，不上明细表 | 已出量、需求日、一级/二级分类、编码、序号、克重 |

### 7.3 判定口诀

> **用户在这一屏做决定时，会看这个字段吗？**
> 会 → 保留（并归入决策/约束档）
> 不会 → 挪走或删（归入历史/上下文档）

### 7.4 结构性原则

| 原则 | 说明 |
|---|---|
| **档案属性不入明细表** | 名称 + 分类 + 编码 + 规格 = 四者表达同一件事，只留「名称」。「规格」仅当影响决策时保留（如出库按份，需知 g/份） |
| **一套主单位** | 记账主单位是「份」。克重只在台账保留，明细表不并列（避免"计划量(g)"与"计划份数"并存造成误读） |
| **不排版字段入表** | 「序号」是排版辅助，不占数据列 |
| **常量字段不入表** | 若某字段在一屏内恒为同一值（如新模型下出库主体恒为门店），直接删列或降级为标题 |
| **可推导字段不重复表达** | 「是否按计划出库」= 逐行「本次出库 == 应出量」，由明细天然表达，不另设列 |
| **历史进详情，不进列表** | 「已出量」这类过程数据在详情页可见即可，列表页只留当前状态 |

### 7.5 逐页审查结论

| 页面 | 现状字段 | 审查结论 |
|---|---|---|
| **出库单列表** | 序号 / 出库单号 / 出库主体 / 来源单据 / 出库份数 / 合计金额 / 是否按计划出库 / 状态 / 库管负责人 / 创建时间 / 操作 | **删**：序号（排版）、出库主体（恒为门店，常量）、是否按计划出库（可推导）。**留**：出库单号、门店、来源排程单、出库份数、合计金额、状态、库管负责人、创建时间、操作 |
| **出库单详情表** | 一级分类 / 二级分类 / 序号 / 名称 / 封装规格 / 计划出库数(份) / 计划量(g) / 单价 / 本次出库数(份) / 出库量(g) / 金额 / 出库状态 | **删**：一级分类、二级分类、序号、计划量(g)、出库量(g)（一套主单位原则）。**留**：名称、规格、应出量(份)、单价、本次出库(份)、金额、状态。**挪**：缺口 → 汇总条 |
| **出库创建 Step2** | 同详情表 + 可出量 | **删**：已出（由 1:1 必然为 0）、可出量（改作输入框 max）。**留**：见上 |
| **库存列表** | 一级分类 / 二级分类 / 编号 / 名称 / 类型 / 库存份数 / 库存量(g) / 最近变动 | **删**：二级分类、编号（与名称重复）、类型（分类已含）。**留**：一级分类（用于分组浏览）、名称、库存份数、**已预留份数**（新增）、最近变动。**挪**：库存量(g) → tooltip |

| **切配工单表** | 一级分类 / 二级分类 / 编号 / 名称 / 规格 / 计划份数 / 净料用量(g) / 实际完成份数 / 确认结果 / 备注 | **删**：一级分类、二级分类、编号、净料用量(g)（主单位是份）。**留**：名称、规格(g/份)、计划份数、实际完成份数、确认结果、备注 |
| **生产批次卡片** | 标题 / X 张排程 / Y 张内部生产 / 状态 / 制单人 | **删**：Y 张内部生产（概念取消）、X 张排程（对班组长无决策价值）。**留**：批次号、生产日、时段、净料种类数、需求份数、建议生产份数、缺口标记、状态 |
| **生产批次详情 Tab1** | 见 §5.5 | **移**：需求日（整批一致时放表头）、一级/二级分类（进展开区）、实际完成（未确认阶段隐藏或与状态合并）、编码（降级小字） |
| **门店需求 Tab2** | 净料 × 门店矩阵 | 保留（这是决策视图）。仅保留净料名 + 门店名，规格归入 tooltip |
| **排程详情** | 菜品 / 规格 / 计划份数 / 售出 / 差额 / 销售额 … | **新增**：需求 → 已备货 → 已出库 三段进度；其余字段按三档复核 |
| **新建批次页** | 批次属性 / 来源列表 / 汇总表 | 见 §5.4；汇总表列：净料、需求量、可用库存、建议生产、缺口（恰好四档：决策=无（草稿期不可改，改为详情页）、约束=库存/需求、上下文=无） |

## 八、状态机与联动

### 8.1 排程单
`草稿` → `已确认`（可纳入批次） → `已排产`（需求已被批次承接，可被多个批次拆分） → `已完成`（出库单已创建且结算完毕）

### 8.2 生产批次单
`草稿`（可编辑行/加减来源/加自主行） → `已确认`（**重算建议量 + 占用库存** + 生成切配任务） → `已完成`（回填实际产量、入库、核销占用、回写已备货量）

### 8.3 联动规则
- 排程单 → 批次：纳入后 → 已排产；批次作废 → 回到已确认。
- 批次 → 库存：完成生产 `stock_in`（份 + g）。
- 批次 → 门店需求行：按关联表**精确回写**「已备货量」。
- 出库单 → 门店需求行：出库量累计；作废回退。
- 出库单 → 库存：`stock_out` / 作废 `stock_rollback`。
- 出库单 ↔ 排程单：1:1。排程单出库完成 → 状态 已完成。

### 8.4 履约进度可见
门店排程单详情展示三段进度：**需求 → 已备货 → 已出库**，缺口显式标红。这是目前业务人员最缺的信息。

## 九、落地分期建议

### 第一步：生产批次可编辑 + 库存参与净需求（最痛）
- 批次行从 JSON 快照迁为**独立行表**；行记需求日期。
- 新增批次行 ↔ 门店需求行 关联表（支持 N:M 拆分）。
