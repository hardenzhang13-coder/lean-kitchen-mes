# 每日销售数据回录 · 需求讨论

> 阶段一产出物：需求讨论记录。确认后进入 PRD 方案阶段。

---

## 一、背景与现状盘点

**业务链路现状：** 排程 → 采购 → 切配 → 生产，链路已跑通；销售端数据缺失，闭环断在最后一公里。

**代码现状（只读，不可写）：**

| 已有资产 | 位置 | 状态 |
|---------|------|------|
| `schedule_items.actual_sold_qty` 字段（空=未回录） | prisma/schema.prisma | ✅ 已落库 |
| 工作台复盘视图（售出/售出率/营收/售出进度条） | app/page.tsx + /api/dashboard/daily | ✅ 只读展示 |
| 「待回录」占位文案 | 工作台未回录态 | ✅ 已有 |
| 排程完成操作（进行中→已完成） | /api/schedules/[id]/complete | ✅ 已有 |

**缺口：** 无录入入口、无写入 API、无批量导入。售出数据目前没有任何方式进入系统。

## 二、需求目标

1. 厨师长/运营在每天生产结束后，把**每道菜实际售出份数**录回系统（手动 or 导入）
2. 回录后工作台当日复盘单从「计划视图」自动切换为「复盘视图」
3. 复盘数据支撑次日排程决策（哪些菜加量、哪些菜减量）

## 三、关键决策点（本次方案采用的假设）

| # | 决策点 | 方案假设 | 理由 |
|---|--------|---------|------|
| 1 | 回录粒度 | 按排程明细行录入**每菜售出份数**，按天汇总 | 与现有 `actual_sold_qty` 字段和复盘 API 完全对齐，零迁移成本 |
| 2 | 录入节奏 | 支持**部分回录**（先录几道菜保存），也支持一次录完 | 晚市结束晚，可能分批录入；`recorded` 判定本就是 `every(item != null)` |
| 3 | 售出 > 计划 | **允许**，醒目标记「超售 +N」 | 现实会临时加做/补货，不能阻断录入 |
| 4 | 导入格式 | **CSV 模板**（编号/名称/售出份数），解析预览确认制 | 门店 POS/Excel 都能导出 CSV；不对接外卖平台 API（本期不做） |
| 5 | 匹配规则 | 编号精确 > 名称精确 > 别名；同名多菜标记「多义」需人工选 | 避免错配菜品 |
| 6 | 录入入口 | 工作台（主）+ 排程详情页（次），共用同一回录组件 | 工作台是每日复盘主阵地 |
| 7 | 数据模型 | **不新增表**，仅 `schedule_items` 加 `sold_recorded_at` / `sold_recorded_by` 两列 | 最小变更；操作日志走现有 logOperation |
| 8 | 修改已回录数据 | 允许修改，二次确认 + 记录日志 + 展示「最后回录时间/操作人」 | 产品原则：可追溯 |
| 9 | 临时加菜（未排程菜品卖出） | 不单独录入，用「超售」覆盖该场景 | 控制 v1 范围 |

## 四、明确不做（v1 范围外）

- ❌ 按时段分段录入（午市/晚市分开）——按天汇总够用
- ❌ 销售流水明细（逐笔订单）——只录每菜总份数
- ❌ 自动对接 POS / 外卖平台 API——只支持 CSV 文件导入
- ❌ 无排程的独立销售单录入
- ❌ 销售趋势报表 / 菜品售卖排行页——复盘视图已承载决策信息
- ❌ 渠道拆分（堂食/外卖）

## 五、待确认问题

1. CSV 模板列定义：`编号,菜品名称,售出份数` 三列是否够用？（方案：编号可空，空则按名称匹配；名称列做展示对照）
2. 售出份数是否允许小数？（方案：允许 0~9999 的整数；份数按整份售卖，不支持 0.5 份）
3. 已完成状态的排程是否允许补录/修改？（方案：允许，便于补账）

## 六、第二轮讨论（2026-11-09 · 用户反馈后修订）

### 反馈与结论

| 用户反馈 | 结论 |
|---------|------|
| 「回录入口应放在排程单详情页」 | ✅ 采纳。销售回录是**排程单的生命周期动作**（计划→生产→售出），归属详情页才符合单据视角。工作台保留复盘数据展示，但降级为「只读窗口 + 跳转入口」 |
| 「一级菜单应增加数据报表模块，名字待定」 | ✅ 采纳。命名候选：**数据报表**（推荐，中性覆盖）/ 经营报表 / 报表中心 / 数据洞察。原型先用「数据报表」，改名仅一处文案 |

### 修订要点

1. **入口重定位**：详情页新增第 4 个 Tab「销售回录」（与排程菜单/切配工单/采购计划并列），未回录时 Tab 带 amber 徽标提醒；页头加一条轻量横幅「本排程尚未回录销售数据 → 去回录」。工作台当日卡片的「回录售出」按钮改为跳转详情页（或仅保留数据展示）。
2. **数据报表模块**（一级菜单，路由 `/reports`）：
   - 两个 Tab：**菜品销售**（按菜品聚合售卖表现：售出率/销售额/毛利，滞销标黄）+ **排程复盘**（按天列出各排程计划 vs 实际，点击进详情）
   - 维度：日期范围（近7天/近30天/本月）+ 门店
   - 报表只做「能驱动次日排程决策」的最小集，不做花里胡哨的大屏（产品原则保持）
3. 回录弹窗组件（手动/导入双 Tab）不变，整体迁移至详情页复用。
4. 新增 API：`GET /api/reports/dish-sales`、`GET /api/reports/schedule-review`（均需分页，遵守无分页列表 API 禁令）。

### 数据模型补充（在 v001 基础上）

- 报表数据全部由 `schedules` + `schedule_items.actual_sold_qty` 聚合得出，**不新增表**；后续若售出数据脱离排程（如未来接 POS），再考虑独立销售流水表。
