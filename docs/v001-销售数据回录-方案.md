## 一、产品目标

补全「排程 → 采购 → 切配 → 生产 → **销售回录**」闭环的最后一段：让每天的实际售出份数以最低成本进入系统，使工作台当日复盘单从计划视图切换为真实复盘视图，支撑次日排程的加量/减量决策。

### Success Metrics

| 指标 | 定义 | 目标 |
|------|------|------|
| 回录及时率 | 生产日当天 22:00 前完成全部回录的排程占比 | ≥ 90% |
| 录入耗时 | 单道菜的售出录入操作耗时 | ≤ 10 秒/菜 |
| 导入成功率 | CSV 导入行匹配成功率 | ≥ 95%（编号匹配） |
| 回录覆盖率 | 已生产排程中完成回录的占比 | 100%（工作台强提醒） |

## 二、用户故事

| 角色 | 故事 | 验收要点 |
|------|------|---------|
| 厨师长 | 晚市结束后，在工作台点「回录售出」，逐菜填售出份数，保存后立刻看到售出率和营收 | 部分回录可保存；售罄快捷操作；保存即刷新复盘视图 |
| 厨师长 | 门店 POS 导出了 CSV，我直接上传，系统自动匹配菜品，确认后完成回录 | 未匹配行可见可处理；确认前不入库；覆盖提示 |
| 运营人员 | 昨天录错了宫保鸡丁的售出数，今天我要改掉 | 已回录可修改，有二次确认，留操作日志 |
| 厨师长 | 第二天排程时，我想知道昨天哪些菜滞销 | 复盘视图按售出率降序，滞销菜沉底并标黄 |

## 五、交互流程与状态定义

### 5.1 状态机（单条排程明细）

```
未回录(null) ──录入──> 已回录(n) ──修改──> 已回录(n')
     ↑__________________|
   （清空输入并保存 = 回到未回录）
```

排程级状态派生：
- `partial`：≥1 条且非全部已回录 → 头部「已回录 x/y 道」黄色提示
- `recorded`：全部已回录 → 工作台切换复盘视图（现有 API 判定逻辑不变）

### 5.2 关键交互

| 场景 | 规则 |
|------|------|
| 售出输入校验 | 整数 0~9999；空=未录；非数字/超范围行内红框提示并阻断保存 |
| 超售 | 售出>计划时不阻断，行内红 badge「超售 +N」 |
| 售罄快捷 | 点击「售罄」= 填入计划份数；「全部售罄」= 所有未录行填入计划份数 |
| 部分保存 | 允许；toast「已保存 3/8 道，可随时继续回录」 |
| 修改已回录 | 弹窗预填现有值，保存前 confirm「将覆盖 8 道菜的回录数据」 |
| 导入解析 | 客户端解析（复用 lib/client/csv），不入库；确认后整体提交 |
| 导入冲突 | 目标菜已有售出值 → 「将覆盖」badge，确认弹窗提示覆盖行数 |
| 重复行 | 同菜品多行 → 自动合并求和，🔶 badge 提示 |
| 空售出列 | 该行不导入（视为未录） |

### 5.3 异常与空态

- 当日无排程：不显示回录按钮（现状保持）
- CSV 解析失败（编码/列不对）：错误提示 + 模板下载链接
- 全部行未匹配：确认按钮禁用，提示检查编号/名称
- API 失败：toast 错误 + 弹窗保持数据不丢失

## 六、数据与 API 设计

### 6.1 Schema 变更（最小）

```prisma
model ScheduleItem {
  // 已有：actualSoldQty Decimal?
  soldRecordedAt DateTime? @map("sold_recorded_at") // 本行最后回录时间
  soldRecordedBy String?   @map("sold_recorded_by") // 本行最后回录人
}
```

迁移：`20261107xxxxxx_add_sold_record_meta_to_schedule_items`，migrate diff 零差异校验。

### 6.2 API

**POST /api/schedules/[id]/sold-records** — 批量写入（手动/导入共用）

```typescript
// 请求
{
  items: [{ itemId: number, soldQty: number | null }], // null = 清除回录
  source: "manual" | "import",
  fileName?: string // import 时记录来源文件
}
// 响应：{ code, data: { updatedCount, partial, summary } }
```

必选清单对齐：zod 校验（itemId 属于该排程、soldQty 0~9999 整数或 null）→ 事务 `prisma.$transaction` 批量 update → `logOperation`（含来源与文件名）→ 返回复盘 summary（复用 dashboard/daily 的计算逻辑，抽公共函数）。

**GET /api/dashboard/daily** — 增量补充 `soldRecordedAt/By`（取每排程明细最大值）与 `partial` 派生态，供头部「已回录 x/y 道」展示。

CSV 模板：前端静态生成下载（表头 `编号,菜品名称,售出份数` + 当前排程全部菜品行，编号列预填、售出列留空）。

### 6.3 权限

沿用现状（无复杂角色体系）：PC 端登录用户均可回录，操作人取 session 写入 `soldRecordedBy` 与操作日志。

## 七、埋点与追溯

- 每次写入/修改记录 `logOperation`：动作、排程编号、变更行数、来源（manual/import + 文件名）、操作人
- 明细行级 `sold_recorded_at/by` 支持「谁最后改了这道菜」追溯
