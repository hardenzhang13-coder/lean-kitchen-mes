# 重大协作错误清单

> 记录协作过程中出现的**重大错误**，目的是不要犯第二次。
> 记录原则：只记事实、不找借口、每条都要有可执行的改正动作。
> 维护：每次出现重大协作错误即追加；每季度回顾一次，尝试删除已稳定改进的条目。
> 创建于 2026-11-15

## 使用方式

新增条目格式：

```
**发生时间**：YYYY-MM-DD HH:MM

**根因**：{为什么会犯}
**改正**：{今后具体怎么做}
**检查点**：{可以自动/半自动拦截的手段，没有就写「无」}
```

## E1 · 凭周边环境推断外部配置，忽略了用户刚做的配置

**发生时间**：2026-11-15 00:10 前后
**场景**：准备把代码部署到生产。需要判断能否走 ACR 镜像路径（`deploy.yml` 的 `build` job 条件是 `vars.ACR_REGISTRY != ''`）。
**错误**：我只查了生产服务器上的 `.env`（里面当然没有 ACR 变量），看到 `docker compose config` 解析出 `lean-kms-web:local`，就断定"ACR 没配、CI 触发不了"，直接改走现场构建。**实际上用户当天刚花时间配好了 ACR**，GitHub Actions Variables 与 Secrets 均已就绪。
**代价**：用户专门投入的配置被"视而不见"；现场构建多耗时约 15 分钟；ACR 通路至今没有实测验证。
**根因**：用"我能方便查到的证据"代替"配置的真正来源"；并且在本机缺少 `gh` CLI 时过早下结论，没有尝试凭据管理器里已有的 GitHub 凭据调 API。
**改正**：
1. 判断某个外部系统（GitHub Actions / ACR / 云控制台）的配置状态，**必须直接查配置源**，不能从服务器 `.env`、本地 CLI 缺失等周边现象推断。
2. 本机缺 CLI 不等于无法访问 —— 先尝试 `git credential fill` + REST API，再下"无法访问"的结论。
3. 用户说"我今天专门做了配置"这类话，视为**强信号**：先验证用户的陈述，再看自己的证据。

**检查点**：无自动手段。人工习惯：写"某配置不存在"这类结论前，先问「这个配置到底写在哪个系统里？」并去那里看。

## E2 · 长耗时命令静默执行，十多分钟无任何反馈

**发生时间**：2026-11-15 00:00–00:20
**场景**：在生产服务器执行 `docker compose up -d --build`（现场构建，约 15 分钟）。
**错误**：命令用了 `... 2>&1 | tail -60` 管道，输出被缓冲到命令结束才吐出。执行期间终端完全静默，我也没有向用户说明预计耗时，更没有中途汇报进度。用户直接问出"这么久了，你现在在干啥"。
**代价**：用户无法判断我是卡住了、在跑还是已完成，只能中断轮询来问；对"生产环境操作"这种高风险场景，静默尤其不可接受。
**根因**：把"减少输出噪音"当成了优化；但对长耗时操作，真正的噪音是**没有进度**。
**改正**：
1. 超过 1 分钟的命令，一律**流式输出**（不加 `tail` 缓冲），或分段汇报。
2. 开工前先说一句预计耗时（如"现场构建约 15 分钟，我会中途汇报"）。
3. 长轮询脚本内部要打印心跳（每轮打印时间戳与状态），且**必须用 session 方式**让用户能随时看到。

**检查点**：命令超过 60 秒 → 输出里带进度行。

## E3 · 生产数据比对命令传参写错，制造了一次"数据全变了"的假警报

**发生时间**：2026-11-15 00:22
**场景**：部署完成后比对生产库基线，确认食材/菜品数据未被改动。
**错误**：把 SQL 直接内联进 SSH 的双引号命令里，`$MYSQL_ROOT_PASSWORD` 被 PowerShell 提前处理，mysql 实际只收到一个残缺命令，输出仅 1 行。比对脚本因"后"侧文件几乎为空，**报出"差异 25 行 / 25"** —— 看起来像是全库数据被改动。
**代价**：如果当时没复核就下结论，会造成一次完全错误的"生产数据丢失"告警，直接打击用户对系统的信任，也浪费一轮排查。
**根因**：比对脚本把"输出为空"当成了"数据不同"，没有先校验输出是否合法（行数是否符合预期）。
**改正**：
1. **生产数据类结论，必须先校验命令输出本身有效**（行数、首行格式、是否含 ERROR），再做比对。
2. SQL 一律走**本地文件 → 管道到远端**的方式（`Get-Content file | ssh ...`），不内联拼接。
3. 比对脚本要区分"两侧都存在但内容不同"与"一侧缺失"，缺失时直接判为**命令失败**而非数据差异。

**检查点**：比对前加断言 —— 两侧行数必须相等且 ≥ 预期最小值，否则中止。

## E4 · 首次 SQL 失败时用 `2>/dev/null` 吞掉错误信息

**发生时间**：2026-11-15 00:15
**场景**：生产库首次执行盘点统计（多条 SELECT）。
**错误**：远端命令写成 `mysql ... 2>/dev/null`，报错信息被丢弃，只看到一个空输出和退出码 1，无法判断是语法错、字段不存在还是连接问题。
**代价**：白跑一轮，且因为看不懂失败原因，退回去改用逐条拆分重试，多花了两轮往返。
**根因**：为了"输出干净"而屏蔽了 stderr，但当时正是**最需要** stderr 的场景。
**改正**：排查阶段一律**保留 stderr**；只有在确认输出会被消费、且已验证命令正确时才过滤。

## E5 · 部署前没有主动审计"这次部署会写生产库的什么"

**发生时间**：2026-11-15 00:05–00:12
**场景**：准备把包含 schema 变更的提交部署到生产。
**错误**：我最初只核对了**新增迁移**的内容（确认它只有 CREATE TABLE + INSERT IGNORE），**没有审计 `prisma/seed.ts`** —— 而生产 `migrate` 服务的启动命令是 `prisma migrate deploy && prisma db seed`，seed 才是真正可能覆盖生产字典的那一环。是用户提醒"不要把食材和菜品数据更新没了"之后，我才回头逐行审计 seed。
**代价**：部署前最关键的安全判断被推迟；且我最初的判断依据不完整（只覆盖了迁移，没覆盖 seed）。
**根因**：把"部署 = 应用迁移"当成了等价于"部署 = 应用迁移 + 跑种子"。
**改正**：**部署前强制做三件事**，缺一不可：
1. 逐行读一遍本次涉及的**所有**迁移文件，确认没有 UPDATE/DELETE 业务表；
2. 逐行读一遍 `prisma/seed.ts` 的所有写操作，列出它会碰的表与"覆盖语义"；
3. 在生产库跑一次**只读盘点**，确认待处理数据的真实形态，再决定要不要动。

**检查点**：`docker-compose.yml` 的 migrate 服务命令若含 `db seed`，则 seed 审计为部署前必查项。

## E6 · 直接继承历史结论，未用生产实际数据复核

**发生时间**：2026-11-15 00:10
**场景**：`memory-bank/progress.md` 记录了一条待办 ——"存量净料/小料需补齐 `packageSpec`，否则完成生产/出库报错"。
**错误**：我在准备生产数据处理方案时，先把这条当成了既定事实。实际到生产库一查：**70 条净料/小料全部已有有效封装规格（5g~2000g，0 缺失）**，这条待办根本不存在。
**代价**：若不复核，会为不存在的问题去打扰厨师长和运营做一轮无意义的填表确认。
**根因**：把项目文档里的结论当成了当前状态。文档是**上一次写入时的快照**，生产库才是事实。
**改正**：凡是"待办/遗留问题"类结论，**动手前必须用只读查询复核一遍**；文档与实际不符时，以实际为准并回头修正文档（本次已在 `memory-bank/progress.md` 中关闭该待办）。

## E7 · 反复并发执行大批量命令，缺少阶段性结论

**发生时间**：2026-11-15 全程
**场景**：生产盘点与部署验证阶段。
**错误**：连续抛出多条长命令（盘点、基线、部署、比对），中间没有把"已经拿到什么结论"讲清楚，导致整体节奏显得拖沓，也让用户难以判断进度。
**代价**：用户在多轮等待后不得不直接打断询问进度。
**根因**：把"连续执行"当成推进效率，忽略了**结论的交付节奏**。
**改正**：
1. 每完成一个阶段，先给一句**结论式汇报**（"已确认 X，Y 是 Z"），再执行下一阶段。
2. 连续工具调用不超过 2–3 个批次。
3. 每批命令的目标不同（探查 / 执行 / 验证）时，不要混在同一批里。

---

## 通用准则（从以上条目提炼）

1. **结论要有出处**：凡是"某配置不存在""某数据有问题""某功能不可用"的判断，都要指明是从哪个系统、哪条命令看到的。
2. **用户的陈述优先于我的推断**：用户说他做过某事，先验证他的陈述。
3. **生产操作三件套**：只读盘点 → 可回滚备份 → 明确回滚路径，然后再动写操作。
4. **静默即风险**：超过 1 分钟的命令必须有进度输出。
5. **区分"命令失败"与"数据异常"**：任何自动化比对，都要先验证输入有效性。
6. **阶段性汇报**：每阶段一句话结论，不让用户靠追问获取进度。
